================================================================================
"can you move up the solution for this? ... have it run every 2 hours. first export."
**"FIRST EXPORT" IS THE DESIGN AND MUST NOT BE WEAKENED.** Six times an hour instead of twice a day
means the delete step runs six times more often, so verify-before-delete matters MORE, not less. Do
not "optimise" it away because the batches are small.

================================================================================
THREE CONSEQUENCES OF 2 HOURS THAT ARE NOT JUST A SMALLER NUMBER
================================================================================
 1. *** THE FIRST RUN IS NOT LIKE THE OTHERS AND WILL HURT IF YOU TREAT IT THE SAME. ***
    Steady state a 2-hourly job with a 48h cutoff moves ~2 hours of aged-out rows - at the measured
    5-11 GB/day that is only ~0.4-0.9 GB per run. **But the first run faces the whole accumulated
    stock: ~18 GB of TOAST, 9.88M chunks, everything older than 48h back to 2026-03-29.** Exporting
    and deleting that in one transaction against the LIVE prod router's database is exactly the kind
    of long-running statement that causes the outage this task exists to prevent.
    **REQUIRED: chunk the backlog drain.** Bound each pass by row count or a moving time window
    (oldest day first), commit per chunk, and let the schedule work through the backlog over several
    runs. **State the chunk size you chose and why.** A first run that tries all 18 GB at once is a
    FAILED design, not an ambitious one.

 2. **`VACUUM FULL` IS OFF THE TABLE ENTIRELY, and plain autovacuum is the point.**
    It takes an ACCESS EXCLUSIVE lock on a table the live gateway writes to on every single request.
    Six times a day is not a "window", it is a recurring outage. The scheduled job does DELETE only
    and relies on autovacuum marking pages reusable so Postgres REFILLS them - **that is what keeps
    the table FLAT** once the stock is drained. Confirm `n_dead_tup` is not climbing run over run and
    say so in the audit entry; if it climbs, the job is losing to the write rate and that is a
    finding. The one-time reclaim of the existing 18 GB is `pg_repack` in an attended window with
    Paxton's go - **do NOT fold it into the schedule.**

 3. *** NON-OVERLAP IS NOW A REAL RISK, NOT A FORMALITY. ***
    At 12h a run could not realistically collide with the next. At 2h, a slow NAS transfer or a large
    chunk can still be running when the timer fires. Implement the SKIP path with a **real lock** - a
    lock file with a stale-lock timeout, or systemd single-instance semantics - and
    **TEST IT BY DELIBERATELY OVERLAPPING TWO INVOCATIONS.** Two concurrent runs both deleting by
    cutoff is how rows get deleted that were never verified at the far end.
    A skipped run writes a **SKIPPED** audit entry (125b's path) and exits. It does not run silently.
