THE ORDER OF OPERATIONS IS THE WHOLE SAFETY DESIGN - DO NOT REARRANGE IT
================================================================================

This deletes production data. The sequence below is not a suggestion:

  1. **Pick a cutoff** - an explicit timestamp, e.g. rows with `"startTime" < now() - interval
     '48 hours'`. Never "everything"; recent rows are what an operator debugging a live incident
     needs. Record the cutoff in the audit entry.
  2. **EXPORT FIRST** to a temp file on CT202, compressed. Record the exact row count exported.
  3. **TRANSFER** to `/Volume2/cognizioware-mcp-gateway/spendlogs/` on terranas01.
  4. **VERIFY ON THE DESTINATION** - re-read the file ON TERRANAS01 and confirm both a checksum
     match and the row count. **A successful scp exit code is NOT proof the bytes are readable at
     the far end.** If verification fails: STOP, delete NOTHING, write a FAILED audit entry.
  5. **ONLY THEN DELETE**, and only rows at or before the same cutoff, bounded by the same
     predicate used for the export - not a fresh `now()`, or you delete rows written between steps
     2 and 5 that were never exported.
  6. **RECLAIM** - `DELETE` does not return space to the filesystem in Postgres. A plain `VACUUM`
     marks pages reusable; only `VACUUM FULL` returns space to the OS and it **takes an exclusive
     lock on the table**. Decide deliberately and say which you chose and why. **VACUUM FULL MUST NOT be in the 2-hourly path at all** -
     see the cadence decision block at the end of this file.
  7. **AUDIT ENTRY, ALWAYS** - success or failure, see below.

The cadence is now **every 2 hours**, not 12. This task is also moved UP the queue by Paxton's

"FIRST EXPORT" IS ALREADY THE DESIGN AND MUST NOT BE WEAKENED. The order above -
cutoff, EXPORT, TRANSFER, VERIFY ON THE DESTINATION, only then DELETE - is unchanged. Six times an
hour instead of twice a day means the delete step runs six times more often, so the verify-before-
delete gate matters MORE, not less. Do not "optimise" it away because the batches are small.

THREE CONSEQUENCES OF 2 HOURS THAT ARE NOT JUST A SMALLER NUMBER. Address each explicitly:

 1. **THE FIRST RUN IS NOT LIKE THE OTHERS AND WILL HURT IF YOU TREAT IT THE SAME.**
    Steady-state, a 2-hourly job with a 48h cutoff moves roughly 2 hours of aged-out rows - at the
    measured 5-11 GB/day that is only ~0.4-0.9 GB per run. But the FIRST run faces the whole
    accumulated stock: ~18 GB of TOAST, 9.88M chunks, everything older than 48h back to 2026-03-29.
    Exporting and deleting that in one transaction on the LIVE prod router's database is exactly the
    kind of long-running statement that causes the outage this task exists to prevent.
    **REQUIRED: chunk the backlog drain.** Bound each pass by row count or by a moving time window
    (e.g. oldest day first), commit per chunk, and let the schedule work through the backlog over
    several runs. State the chunk size you chose and why. A first run that tries to do all 18 GB at
    once is a FAILED design, not an ambitious one.

 2. **AT 2 HOURS, `VACUUM FULL` IS OFF THE TABLE ENTIRELY - and plain autovacuum is the point.**
    It takes an ACCESS EXCLUSIVE lock on a table the live gateway writes to on every single request.
    Six times a day is not a "window", it is a recurring outage. The 2-hourly job does DELETE only,
    and relies on autovacuum marking those pages reusable so Postgres REFILLS them with new rows.
    That is what actually keeps the table FLAT: once the stock is drained, the file stops growing
    because deletes and inserts trade the same pages. Steady-state needs no VACUUM FULL ever.
    Confirm autovacuum is actually keeping up on this table (`n_dead_tup` in `pg_stat_user_tables`
    should not climb run over run) and say so in the audit entry - if dead tuples climb, the job is
    silently losing to the write rate and that is a finding.
    **The ONE-TIME reclaim of the existing 18 GB still needs `pg_repack` in a deliberate window.**
    That stays a separate, attended step with Paxton's go. Do not fold it into the schedule.

 3. **NON-OVERLAP IS NOW A REAL RISK, NOT A FORMALITY.**
    At 12h a run had no realistic chance of colliding with the next. At 2h, a slow transfer to the
    NAS or a large chunk can still be running when the timer fires again. The SKIP path (previous
    run still going -> write a SKIPPED audit entry and exit) must be implemented with a real lock -
    a lock file with a stale-lock timeout, or systemd's own `RefuseManualStart`/single-instance
    semantics - and it must be TESTED by deliberately overlapping two invocations. Two concurrent
    runs both deleting by cutoff is how rows get deleted that were never verified at the far end.

AUDIT ENTRY ADDITION: because the cadence is now 12 entries a day, the audit surface must stay
readable. Keep ONE entry per run as specified, but make the SKIPPED/SUCCESS/FAILED outcome the
primary sortable field so an operator can find the failures without reading 84 rows a week. Do NOT
add a second page or view for this - the RULE 2 constraint against duplicating surfaces is unchanged.
