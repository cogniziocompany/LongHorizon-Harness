WHY THIS EXISTS. Today's orchestrator is `launch_queue.py`, a polling script on a Windows workstation that reads JSON files from a directory, decides a model trio, enforces a run cap, and POSTs to the harness API. It is a stopgap. On 2026-09-08 it produced, in one day: three copies of itself running simultaneously and racing the same queue directory (a `pkill` from Git Bash does not kill Windows processes, so each "restart" stacked another); six runs killed at round zero because it had no idea a provider deployment was rate-limited and in cooldown; three hand-edits to the role/model dict as availability moved; and a queue that stops entirely whenever the workstation sleeps, reboots or loses its network. None of these are bugs in the script. They are the consequence of an orchestrator living outside the system it orchestrates.

THE TARGET. The chat agent at chat.easybutt0n.ai becomes the orchestrator: a person or an agent asks for work in chat, the chat agent writes a queue entry through the harness's own API, and the harness service on CT110 owns launching, routing, budgets and reporting. The PC script is decommissioned. Deliver a plan precise enough that someone can execute it without re-deriving any of this.

PRIMARY DELIVERABLE - `docs/handoffs/orchestrator-migration-2026-09-08.md`, structured as follows. Be concrete; a plan that says "wire up the chat agent" is a failure.

 (1) INVENTORY - every behaviour the PC launcher performs today, each as a numbered row, and for each: what it does, what breaks if it is lost, and who owns it after migration. Read the script's behaviour from THIS repo's API surface (webapi/server.py, launcher.py, queue.py, mcp_tools.py) rather than guessing; the script itself is not in this repo and you cannot read it, so the plan must state each behaviour as a CONTRACT the new owner must satisfy. At minimum: polling a queue for pending work; deciding a role/model trio; enforcing a concurrency cap; refusing to launch two runs into one working tree; passing max_rounds and the agent/mcp_profile per role; moving an entry to a terminal state; recording the run id against the entry; retrying or requeueing a failed entry; and surviving a restart without losing or double-launching work.

 (2) OWNER MAP - for each inventory row, name the component that owns it after migration and whether that component EXISTS TODAY, IS IN FLIGHT, or DOES NOT EXIST. Known owners: the harness queue API and launcher service on CT110 (queue.py, launcher.py, POST /api/queue); dynamic model routing (harness task 49, branch feat/dynamic-model-routing, not merged) for the trio decision; workspace contention detection (task 48, PR #8 open) for overlap warnings; the fleet reporter (merged to main 2026-09-08) plus the fleet window for visibility; Hydra as the control plane and the only write surface. Be honest about which rows have NO owner - those are the migration's real work, and the plan is worthless if it hides them.

 (3) THE CHAT AGENT'S CONTRACT - exactly what the chat agent may and may not do. It is an AI with an API key that can cause code to be written, tests to run and deployments to happen, so this section is the safety boundary and must be written as if a confused or adversarial caller is on the other end. Specify: which endpoints and MCP tools it may call (enqueue, read status, read queue, set a route) and which it may NEVER call (abort another owner's run, resolve an approval gate, change budgets, deploy directly); how its key is scoped and which access groups it holds; a hard ceiling on entries it may create per hour and a maximum max_rounds it may request, so a loop cannot spend the fleet's budget; and which actions still require a human, stated as a list rather than a principle. Note explicitly that prod deploys through the lanes are already auto-approved by standing decision and that gates - not the orchestrator - decide; the chat agent must not acquire the power to bypass a gate.

 (4) GAPS WITH NO OWNER - at least these, plus whatever the inventory surfaces:
   - **Shared-infrastructure interlock.** Nothing today prevents an operator or agent restarting a shared dependency while a gate is mid-flight. This actually happened on 2026-09-08: the prod LiteLLM router was restarted during a promotion's eval gate and poisoned its retries. Dynamic routing handles model availability and has no concept of "a gate is running, do not touch this". Propose where this belongs (Hydra is the natural home as the control plane) and what the check looks like.
   - **Single-orchestrator guarantee.** The PC script had none, and ran three times at once. Whatever replaces it must make concurrent orchestrators impossible or harmless - state which, and how it is enforced (a lease, a lock, idempotent enqueue keys) rather than by convention.
   - **Queue durability and ownership.** Entries today are files on one workstation with no backup. Say where they live after migration, what happens to in-flight entries during cutover, and how an entry cannot be launched twice.
   - **Who watches the watcher.** If the chat agent is down, work stops silently. Define the signal that says the orchestrator is alive and where it surfaces.

 (5) CUTOVER SEQUENCE - ordered, each step with its own rollback, written so it can be executed during normal operation rather than requiring a quiet window. It must include a period where BOTH orchestrators are running and the new one is observed but not authoritative, and it must name the specific evidence that promotes the new one to authoritative. Do not propose a big-bang switch.

 (6) DECOMMISSION CRITERIA - the explicit conditions under which the PC scripts (`launch_queue.py` and its companion watchers) are switched off for good, and what is archived first so the behaviour contract is not lost with them.
