================================================================================

1. **Config-sourced models cannot be changed at all through the API.** Measured 2026-09-10 06:4x,
   `POST /model/update` on `qwen3.8-nothink`:
       "Can't edit model. Model in config. Store model in db via `/model/new`. to edit."

3. **The DB already WINS over the file for five whole sections** - `general_settings`, `guardrails`,
   `litellm_settings`, `mcp_servers`, `router_settings`. So the file is already NOT the truth.
   Measured drift right now: `router_settings.allowed_fails` is **file=1, db=50**.

4. **Nine merged alias edits were DEAD on the live router** (measured 2026-09-09). People reviewed
   them, merged them, and they changed nothing, because the DB row won. That is the worst property
   of the hybrid: work that looks shipped and is not.

WHAT TO DELIVER - a plan and tools, in this order
================================================================================

SLICE 1 - INVENTORY. A script that reads `/model/info` and classifies EVERY deployment as
  DB-sourced (UUID id) or CONFIG-sourced (64-hex id), and diffs the live list against
  `infrastructure/litellm-config.yaml`. Output a table: alias, source, api_base, max_input_tokens,
  supports_vision, supports_function_calling, and IN-FILE-BUT-NOT-LIVE / LIVE-BUT-NOT-IN-FILE.
  **This inventory is the deliverable that makes the rest safe.** Nobody currently knows the real
  split; at last count it was 13 CONFIG vs 1 DB just among qwen aliases.

SLICE 2 - MIGRATION TOOL. A script that takes a model_name and recreates it as a DB deployment via
  `/model/new` with identical litellm_params and model_info, then verifies by reading `/model/info`
  back and diffing field-by-field. It must be IDEMPOTENT and it must REFUSE to run if a DB
  deployment with that model_name already exists (or the alias silently ends up load-balanced across
  a stale config copy and a new DB copy - a trap that would look like it worked).

SLICE 3 - THE ORDER OF MIGRATION, written down with reasoning. Do NOT migrate everything at once.
  Propose a sequence by blast radius, lowest first, and say why each is where it is. State plainly
  which aliases are load-bearing for harness runs (the trio table in C:/tmp/launch_queue.py names
  them) and therefore must move in a quiet window even under this scheme.

SLICE 4 - WHAT THE YAML BECOMES. This is the part that must not be got wrong: **the answer is NOT
  "delete the YAML".** Two things are lost if the file simply goes away, and the plan must address
  both:
    a. **Bootstrap.** If the Postgres row set is lost or the stack is rebuilt from scratch, the file
       is what brings the router back. Define the file's new role explicitly as a SEED, and say how
       it is kept adequate for that.
    b. **Reviewability.** A YAML in git gets a PR, a diff and a reviewer. A DB row gets none of
       that. Propose an EXPORT path - a scheduled or CI job that dumps the live model list back into
       a versioned artifact in the repo - so config changes remain auditable after they stop being
       file edits. Without this, migrating to the DB trades one real problem for a different one.

SLICE 5 - the ops-doctor check. There is already a `config_drift` check in
  `infrastructure/docker/ops-control-center/doctor/ops_doctor.py`. EXTEND IT to report the
  DB-vs-CONFIG split and any alias present in the file but shadowed by a DB row. Do NOT add a new
  view or route - the doctor renders on /overview and RULE 2 forbids duplicating surfaces.
