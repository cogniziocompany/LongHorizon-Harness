## ADDED 2026-09-09 BY PAXTON: SHOW THE EMIT-PROBE READINGS IN THE SAME PLACE
"all this emit should be displayed in the web UX for the user." The outage log answers *what broke and when*; the emit readings answer *is it healthy right now*. They belong on the same page - a reader looking at an OPEN incident immediately wants to know whether the provider is answering this second, and making them open a second surface to find out is the failure this page exists to fix. **Do NOT build a separate health page.**

WHAT THE EMIT PROBE IS. Before committing a 30-minute round, the launcher asks each of a run's three role models to emit one token and times it on the STREAMING path, using the harness's own virtual key. A backend that cannot emit within ~3s is starved, and the run is held rather than launched. A second probe now also runs MID-ROUND (`C:/tmp/spin_watchdog.py`): when a round has been going a long time it re-probes that run's bound executor, which is what distinguishes a starved backend from a model genuinely working - the two look identical from outside at minute ten.

WHAT TO DISPLAY, per model:
 - the alias, and **the model actually SERVED** for it - these differ, and that is not a curiosity: `kimi-k3:cloud` is served by `glm-5.3-flash:cloud` via a fallback chain, so anything that picks models by name is being quietly lied to. Read it from the `message_start` event.
 - **time to first token** from the most recent probe, and when that probe ran.
 - a plain healthy / slow / not-answering state, with the ~3s budget shown so the number means something.
 - which harness ROLE the model currently serves (manager / executor / auditor), or none.
Order so the unhealthy ones are visible first. If a reading is stale, say how old it is rather than presenting it as current - a stale green light is worse than no light.

WHERE THE DATA COMES FROM. Prefer having the launcher and watchdog WRITE their existing probe results to a small file the page reads, over the page probing models itself. A page that probes on render bills a request per model per page load against a pack limited to 2500 requests per 5 hours, and would be a self-inflicted outage. If you conclude the page must probe, cap and cache it, and say exactly why.

CALIBRATION TRAPS - all three cost real time tonight, do not repeat them:
 - measuring time to a TEXT delta with a small token budget fails every thinking-capable model, because the thinking block eats the budget. Accept any content event; the question is whether the backend is SERVING, not what it says.
 - responses are cached, so a probe without a nonce can return in 0.0s and make a dead backend look instant.
 - probing with the master key passes models the harness cannot actually reach. Use the harness's own key, or the reading is about the wrong credential.

WHY THIS MATTERS FOR THE LOG, and it is the whole point of the entry:
An operator seeing "Synthetic: limited" cannot tell whether to wait two hours or go and pay. The status code
is the discriminator and it is already in the error body we receive. **The log must record the CODE and the
verbatim message, and derive the reset clock from the code** - 429 gets a countdown, 402 gets an action item
and NO countdown. Do not collapse them into one "rate limited" state.

Note also, because it will confuse whoever writes the mapping: a 429 body can name a DIFFERENT cause than the
code implies. `glm-5.3:cloud` returned 429 with "retired at" in the body - the alias resolved onto a retired
backend. Record the body verbatim rather than re-deriving a reason from the code alone. That specific
alias-substitution defect belongs to task 64, NOT to this task - do not try to fix routing here.

Ollama Cloud, measured the same tick for contrast (7 of 7 `:cloud` aliases, all 429):
     "you (prax211) have reached your weekly usage limit, add usage credits: https://ollama.com/settings"
Note it names the ACCOUNT (`prax211`) in the message. That is the field that tells an operator WHICH tier is
