## Context

The AI Gateway admin UI's **Response Cache → Cache Health** panel reports:

```
Cache Status: unhealthy
Error Message: Cache not initialized. litellm.cache is None
litellm_settings.cache_params: {}
```

This is not a fault — it is an accurate report that caching was **never configured**.
Verified live on CT202 (2026-09-07):

- 48 containers running; **none is a Redis/valkey/keydb**.
- `cognizioware-mcp-tools-litellm` has **no `REDIS_*` or `CACHE_*` env**.
- `infrastructure/litellm-config.yaml` has **no `cache:` / `cache_params:` key** — the word
  "cache" appears only in comments (`:66`, `:634`). Live copy on CT202 matches the repo.
- Recursive grep for `redis|valkey|keydb` across `infrastructure/**` → **zero hits**. This
  would be the stack's first cache backend.
- Good news: **`redis-py 5.3.1` is already inside the pinned LiteLLM image**, so no image
  rebuild or digest change is required.

**Outcome wanted:** a real, persistent-across-restarts response cache so the health panel
reports healthy, repeated/retried completions and embeddings stop re-billing upstream
providers, and the "Coordination Redis" tab has a backend.

### Decisions taken (confirmed with the user)

| Decision | Choice |
|---|---|
| Backend | **Redis container on CT202** (not in-memory; Postgres is not a supported LiteLLM cache backend) |
| Multi-tenant isolation | **Namespace per key/team** — this router is shared across 20+ virtual keys/teams, and LiteLLM's default cache key is derived from model+messages+params, *not* the caller. Without namespacing, tenant A can be served tenant B's completion. |
| Scope + TTL | **All supported call types, 300 s TTL** — primarily deduplicates retry storms and identical repeated calls rather than acting as a long-lived cost cache. |

## The hard constraint: the UAT lane does not create services

`.github/workflows/deploy-mcp-tools.yml` job `deploy-uat-litellm` (lines 306-453) targets
**CT204 (192.168.21.162:4000)**. It syncs `litellm-config.yaml`, `hooks/`, and
`docker-compose.yml`, pulls the pinned digest, then runs:

```
docker compose up -d --no-deps --force-recreate litellm-router
```

`--no-deps` means **a new `redis` service in compose is never created on CT204.** The
prod `deploy` job is gated on `qa-gate-uat` succeeding, so if CT204's router comes up with
a cache pointing at an unresolvable `redis` host, the whole pipeline blocks — or worse,
passes while silently degraded. This is the same class of hazard documented in
`design docs/handoff-docs/pac-mcp-and-dataverse-data-mcp-handoff.md:269-300`.

**Mitigation, and it is a required operator step before merge:** stand the Redis container
up on CT204 *by hand* first (§3 below), so the config lands on a host that already has a
backend. Do not rely on the workflow to do it.

Second constraint, from `infrastructure/scripts/safe-recreate.sh:5-19`: that script
snapshots the **running** container's resolved env and feeds it back as `--env-file`. A
brand-new `REDIS_PASSWORD` will resolve to empty on a safe-recreate unless it is written
into the on-box `mcp-tools.env` **first**. Order matters.

Third, the **live-env durability rule** (CLAUDE.md): CT202's `mcp-tools.env` is gitignored
and overwritten by every deploy (`deploy-mcp-tools.ps1:97-101`). Non-secret values must be
compose defaults; secrets must be a runbook entry. Applied below.

## Implementation

### 1. Add the Redis service — `infrastructure/docker-compose.yml`

Insert after the `postgres` service (`:250-276`), mirroring its conventions exactly.
**No named volume**: this is a pure cache, deliberately non-persistent — CT202's rootfs is
at **79% (8.5 G free)**, and cache data is disposable by definition.

```yaml
  # ── Redis — LiteLLM response cache + coordination (added 2026-09-07) ─────
  # Pure cache: no RDB snapshots, no AOF, no volume. Data is disposable by
  # design; CT202 rootfs is tight (79% used). maxmemory + allkeys-lru bounds
  # RAM so a cache blowout can never OOM the container the way the 2026-06-25
  # incident 502'd every endpoint.
  redis:
    image: redis:7-alpine
    container_name: cognizioware-mcp-tools-redis
    command: >
      redis-server
      --save ""
      --appendonly no
      --maxmemory ${REDIS_MAXMEMORY:-512mb}
      --maxmemory-policy allkeys-lru
      --requirepass ${REDIS_PASSWORD}
    env_file:
      - /opt/cognizioware-mcp-tools/mcp-tools.env
    environment:
      REDIS_PASSWORD: "${REDIS_PASSWORD}"
    # Not published to the host: only the compose network needs it. (Postgres
    # publishes 127.0.0.1:5432 for admin psql; there is no equivalent need here.)
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "redis-cli -a \"$$REDIS_PASSWORD\" ping | grep -q PONG"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s
    logging:
      driver: journald
      options:
        tag: redis-mcp-tools
    networks:
      - cognizioware-mcp-tools
```

### 2. Wire it into `litellm-router` — same file, `:21-172`

Two edits to the existing service block:

- **`environment:`** — add these near the "Core keys" group. They *must* be explicit `${}`
  refs, not env_file-only: `register-mcp-tools-stack.py:91-101` strips `env_file:`
  directives before sending compose to Portainer. Host/port/db are non-secret → compose
  defaults per the durability rule; the password is a secret with no default.

  ```yaml
      # Response cache (2026-09-07). Host/port are non-secret compose defaults
      # per the live-env durability rule; REDIS_PASSWORD is a secret and lives
      # ONLY in mcp-tools.env (runbook: design docs/mcp-placeholder-services-audit-and-plan.md §12).
      REDIS_HOST: "${REDIS_HOST:-redis}"
      REDIS_PORT: "${REDIS_PORT:-6379}"
      REDIS_PASSWORD: "${REDIS_PASSWORD}"
  ```

- **`depends_on:`** — add alongside the existing `postgres` condition:

  ```yaml
      redis:
        condition: service_healthy
  ```

Do **not** add a `redis` entry to `extra_hosts:`. That list is only for hostnames with no
compose service — the comment at `:143-147` records that a stale `cloudflare-mcp` entry
overrode Docker network DNS and left a healthy backend reporting 0 tools for weeks.

### 4. Configure the cache — `infrastructure/litellm-config.yaml`

Insert inside the existing `litellm_settings:` block (`:38-190`), after `drop_params` /
`enable_pre_call_checks` (`:76-77`). Secrets are `os.environ/` refs only, matching the
file's existing convention.

```yaml
  # ── Response cache (added 2026-09-07) ────────────────────────────────────
  # Backing store: in-stack `redis` service (docker-compose.yml). Purpose is
  # de-duplicating retry storms and identical repeated calls, NOT long-lived
  # cost caching — hence the deliberately short 300s TTL.
  #
  # MULTI-TENANCY — READ BEFORE EDITING. This router is shared across 20+
  # virtual keys/teams. LiteLLM derives the cache key from model+messages+
  # params, NOT from the caller, so a flat global cache would let one tenant
  # be served another tenant's completion. The per-caller namespace is applied
  # by the cache_namespacer hook (hooks/cache_namespacer.py) — do not remove
  # it from litellm_settings.callbacks below.
  cache: true
  cache_params:
    type: redis
    host: os.environ/REDIS_HOST
    port: os.environ/REDIS_PORT
    password: os.environ/REDIS_PASSWORD
    ttl: 300
    supported_call_types:
      - completion
      - acompletion
      - embedding
      - aembedding
```

### 5. Per-tenant namespacing — new `hooks/cache_namespacer.py`

The repo already has exactly the right seam: `hooks/thinking_normalizer.py` is a
`CustomLogger` bind-mounted at `/app/hooks` (compose `:40`) and registered at
`litellm-config.yaml:69-70`. Its `async_pre_call_hook(user_api_key_dict, cache, data,
call_type)` signature is verified against LiteLLM v1.100.0 (comment at `:65-68`).

Add a second, small hook next to it that derives a stable namespace from the caller —
`user_api_key_dict.team_id` when present, else a truncated SHA-256 of
`user_api_key_dict.api_key` — and sets it on the outgoing request, then register it:

```yaml
  callbacks:
    - hooks.thinking_normalizer.thinking_normalizer_instance
    - hooks.cache_namespacer.cache_namespacer_instance
```

Keep it fail-open in the same style as the existing hook: if the namespace cannot be
derived, log and return `data` unchanged rather than raising.

> **Verify the mechanism on CT204 before trusting it.** Per-request cache namespacing is
> the one part of this plan I have not confirmed against the running v1.100.0 build. Step 1
> of verification below is an explicit cross-tenant isolation probe, not a formality. If
> per-request `namespace` turns out not to be honoured, the fallback is to have the hook
> inject the tenant discriminator into a field that provably participates in the cache key
> (e.g. a stable `user` / metadata field), re-probed the same way. Do not ship §4+§5 to
