then `verifyAuth` collapses `status === 'unavailable'` to reason `dataverse_unavailable` unless the

**FAILING CLOSED IS CORRECT. THE CLASSIFICATION IS NOT.** A 403 is a PERMANENT authorization
state, not an availability blip. Telling a guest to "try again shortly" invites them to retry
forever against something that will never change, and it tells the operator "Dataverse is down"
when Dataverse is perfectly healthy - `/api/health` reports `dataverse-mcp` ready:true with its
full tool list at the same moment.

A SECOND INSTANCE OF THE SAME MISTAKE, line 406:

    if (!resourceUrl) return { status: 'unavailable', roles: [], cause: 'network' };

"No resource to query" is a CONFIGURATION or NO-ENVIRONMENT-SELECTED state, not a network failure.
It produces the identical misleading "try again shortly". Fix both.

================================================================================
SCOPE
================================================================================

1. **Give `forbidden` its own reason.** Add `dataverse_forbidden` to the `AuthResult.reason` union
   (`auth.service.ts:77-84`) and stop folding it into `dataverse_unavailable`. In `middleware.ts`
   map it to **403**, not 503, with a message that says what is actually true and what to do -
   along the lines of "Your account is signed in but is not permitted to verify access in this
   environment. Ask an environment administrator to grant you a security role." Carry the existing
   partner-referral URL the way `insufficient_permissions` does.
   **Do NOT reuse the `insufficient_permissions` reason** - that one means "we read your roles and
   they were not enough". This one means "we were not allowed to read your roles at all". Keeping
   them distinct is the entire point of #102 and collapsing them re-creates the original bug.

2. **Give `!resourceUrl` its own reason too.** It is not `network`. Distinguish "no environment
   selected/known for this user" from "Dataverse call failed". The former should lead the user to
   the add-an-environment flow, not to a retry.

3. **Break the ladder circularity - the part that actually unblocks Paxton.** A signed-in user with
   ZERO environments must be able to reach the add-an-environment flow WITHOUT first passing a
   Dataverse role query, because there is no environment to run that query against. Establish what
   the minimum trustworthy gate is for that path (a valid, unexpired token for this tenant's app
   registration is the obvious floor) and let the environment-discovery/add flow run behind it.
   **Do not weaken the gate on any route that reads or writes environment DATA** - only the
   discovery/add path. State plainly in the PR what a guest can now reach that they could not, and
   what still requires a role.

4. **Keep the audit trail.** `logAuditEvent` must record the new reasons distinctly, so the next
   operator can tell "guest lacked permission" from "Dataverse was down" by reading the table -
   which is exactly how this bug was found in twenty minutes.

5. **Tests.** `packages/backend/tests/auth-failure-modes.test.ts` already asserts the 503 string at
   lines 225 and 457; those assertions encode the bug and must change with the behaviour. Add cases
   for: Dataverse 403 -> 403 dataverse_forbidden; Dataverse 500 -> 503 unavailable; missing
   resourceUrl -> the no-environment reason; and a guest with zero environments reaching the add
   flow. Stub `globalThis.fetch`; **NO live calls to Microsoft, Dataverse or Stripe.**
