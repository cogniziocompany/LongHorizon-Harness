Task 136 delivered three scripts whose entire premise is: **a 200 from POST /config/update is not

================================================================================
THE FOUR DEFECTS - all in read-back-synthetic-anthropic-fallbacks.py
================================================================================
 1. **SHAPE MISMATCH (lines ~126-158). The primary bug.**
    `fetch_row()` returns the UNWRAPPED `router_settings` content - confirmed by `prepare-...py`
    itself accessing it as `row["fallbacks"]` directly (~:165), NOT `row["router_settings"]["fallbacks"]`.
    But the expected body piped in from `prepare --apply` is WRAPPED: `{"router_settings": {"fallbacks": [...]}}`.
    So `flatten(expected)` yields `{"router_settings.fallbacks": ...}` while `flatten(live)` yields
    `{"fallbacks": ..., "routing_strategy": ..., ...}`. **The key sets never intersect**, so
    `missing_keys` / `extra_keys` fire unconditionally on every run.

 2. **THE DUPLICATE GUARD HAS THE SAME BUG (~:165-166).**
    `rs = live.get("router_settings", {})` is therefore ALWAYS `{}`, so `fb_list` is always `[]`, so
    every one of the five groups is reported as "0 time(s)" and `dup_ok` is ALWAYS False - regardless
    of what is actually in the DB.

 3. **THE DIFF IS UNSCOPED even after 1 and 2 are fixed.**
    The intended body from `prepare.py` contains ONLY `fallbacks`. The live row also contains
    `routing_strategy`, `num_retries`, `timeout`, `retry_after`, `allowed_fails`, `cooldown_time`,
    `allowed_fails_policy.*` and `context_window_fallbacks`. The script would report every one of
    them as `extra_keys`. Its docstring claims it verifies "no other key changed", but it has NO
    baseline to compare those keys against - it currently treats their mere presence as a mismatch.
    FIX: either scope the diff to the `fallbacks` key only, or take a PRE-WRITE BASELINE snapshot and
    diff the other keys against that. If you choose the baseline, the prepare script must emit it.

 4. **THE DOCUMENTED USAGE DOES NOT RUN.**
    The header comment's own example is `prepare-...py --apply | read-back-...py`. But
    `prepare --apply` prints a diagnostic header, a "groups to add" list, a POST-status line, and TWO
    separate `json.dumps(...)` blocks interleaved with plain text (~:171-208). Piped into
    `read-back`'s `load_expected()` (~:100-108, an UNGUARDED `json.loads(raw)`), that raises
    `JSONDecodeError` before the diff logic ever runs.
    FIX: make the handoff machine-parseable - e.g. `prepare --apply --emit-expected <file>`, or put
    the JSON on stdout and ALL prose on stderr, and guard the parse with a clear error.
