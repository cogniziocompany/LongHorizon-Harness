*** PAXTON 2026-09-10 23:50 PT - A NAMED HYPOTHESIS, AND IT OUTRANKS GUESSING. ***
================================================================================
Verbatim: *"if you find the data colect point, look into db option in the app as a buffer"* and
*"or simpler maintainable"*.

**TREAT THIS AS HYPOTHESIS #1 AND TEST IT BEFORE ANY OTHER.** LiteLLM does not write every spend
log straight through - it **queues them in memory and flushes in batches**. If flushes fall behind
the arrival rate, that in-memory queue grows without bound. That single mechanism would explain
BOTH measurements this task starts from, which no traffic-only or cache-only theory does:
  - the **idle drift** (~240-300 MB/h with DRAIN armed and zero harness runs) - a backlog draining
    slowly, or retrying, while nothing new arrives; and
  - the **traffic-correlated spike** (914 MB -> 16.5 GB in ~5 minutes under the deploy lane's E2E
    and health-check traffic) - arrivals outrunning flushes.

**HOW TO TEST IT - cheap, and it is a MEASUREMENT, not a code read:**
 1. Find the flush/queue settings actually IN EFFECT. **RULE 1 applies hard here:** five config
    sections are DB-shadowed on this router and the DB row WINS over the YAML, so reading
    `litellm-config.yaml` proves nothing. Read the live value back.
 2. Correlate queue depth / flush lag against RSS over one growth episode. If RSS tracks backlog,
    the cause is found.
 3. **CHECK WHETHER POSTGRES IS THE REAL BOTTLENECK.** `LiteLLM_SpendLogs` on this same CT202
    Postgres carries ~18 GB of TOAST and 9.88M chunks (see tasks 125a/b/c). A table that large makes
    inserts slower, which lengthens the queue, which grows memory. **If that is the chain, the leak
    and the spendlog bloat are ONE problem, and 125 is already the remedy for half of it.**

**"SIMPLER MAINTAINABLE" IS A CONSTRAINT ON THE ANSWER.** If a bounded buffer, a flush interval, or
a batch size is the fix, prefer that ONE setting over new code. Do not propose a new service, a new
queue, or a new surface. A configuration change with a measurement behind it beats an architecture.

Step 3 of the test plan above guessed that a bloated `LiteLLM_SpendLogs` slows inserts, lengthening
the in-memory flush queue. **Measured against the live database, that chain is NOT supported:**

    LiteLLM_SpendLogs          295,826 live rows   n_dead_tup = 0    26 GB
    pg_stat_activity           1 active, 16 total, **0 waiting on locks**
    container                  Up 2 days (healthy); a bad credential was refused in 0.417 s

`n_dead_tup = 0` means **autovacuum is fully keeping up** - there is no bloat to reclaim and no
vacuum backlog. Nothing is lock-blocked. A database in that state is not the thing throttling
inserts. **So do not start from "Postgres is slow" - it is measurably not.** If the buffer
hypothesis survives, the backlog must come from somewhere else (flush interval, batch size, a retry
loop, or a failure path that never drains), and THAT is what to look for.

**CREDENTIALS CORRECTION THAT WILL COST YOU AN HOUR IF MISSED:** the role is **`litellm_user`** and
the database is **`litellm_mcp_tools`**. An earlier task draft said role `llmproxy`, database
`litellm` - **neither exists**; psql fails with `FATAL: role "llmproxy" does not exist`. Read
POSTGRES_USER / POSTGRES_DB from the container, never from a task file.

**THE REAL SIZE LEVER, AND IT IS NOT THE DATABASE ENGINE:** 26 GB across 295,826 rows is
**~92 KB per row**. That is TOAST - each row carries full request AND response bodies. Paxton's
constraint is *"we dont want to stop the data colection we want to limit the overlaod of size"*, and
those are compatible: the COUNTS, COSTS, LATENCIES, MODELS and TAGS are tiny; the BODIES are the
26 GB. Reducing or truncating stored bodies keeps every operational metric and removes almost all of
the volume. **Check whether that is a LiteLLM setting before proposing any new storage.**

**ON "COMMENT OUT POSTGRES" (Paxton asked):** flag, do not silently act. This router runs
`store_model_in_db: true` - five config sections live in Postgres and the DB row WINS over the YAML,
plus virtual keys, teams and budgets. Removing Postgres would remove the router's config authority
and every virtual key, not just the spend sink. A local/embedded DB is defensible for the SPEND-LOG
SINK specifically; it is not a drop-in for the router's database. Say so plainly in the report.
