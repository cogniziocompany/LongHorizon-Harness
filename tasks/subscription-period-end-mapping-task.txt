TASK 74 - subscriptions.CurrentPeriodEndUtc is never populated (Stripe moved the field)

CONTEXT (all of this was READ from the live prod system on 2026-09-10, do not re-derive it)

While diagnosing the Stripe webhook 500 warning, three prod subscriptions were found with
CurrentPeriodEndUtc = NULL even immediately after a customer.subscription.updated event was
processed successfully (Status='processed', Error=NULL).

Root cause, confirmed against the live event payload for evt_1UCe91CXyLTnTERyEYsxYn2U:

  - The event's api_version is "2025-09-30.clover".
  - On that version Stripe does NOT send current_period_end at the subscription level.
    Top-level `current_period_end` is absent (null).
  - The value lives on each subscription item instead:
    items.data[].current_period_end  ->  1791285712  (2026-10-06T11:21:52 UTC), present and correct.

So UpsertSubscription reads Subscription.CurrentPeriodEnd, gets the default/null, and the column is
never populated. Renewal and expiry tracking silently has no date to work from.

   current_period_end (that is when the customer next needs to pay) and do not throw.

**WHAT MY BRIEF GOT WRONG:** it said `UpsertSubscription` reads `Subscription.CurrentPeriodEnd` and gets a
null. **That property does not exist.** In the pinned **Stripe.net 49.1.0** (confirmed:
`McpCognizioware.BillingService.csproj:28`), `Stripe.Subscription` exposes neither `CurrentPeriodEnd` nor
`CurrentPeriodStart` - **both live on `Stripe.SubscriptionItem`**. So there is no bad read to fix.

**THE ACTUAL DEFECT, and it is simpler:** `UpsertSubscription` in
`src/McpCognizioware.BillingService/Controllers/StripeWebhookController.cs` (~lines 149-194) **never
assigns `CurrentPeriodEndUtc` at all.** Verified by grep: the identifier does not appear in that file.
The entity column exists and is writable - `Models/OnboardingModels.cs:72`,
`public DateTime? CurrentPeriodEndUtc { get; set; }`. Nothing populates it, so renewal and expiry
tracking have no date. The effect is as described; the cause is an omission, not a mis-read.

**THE REFERENCE IMPLEMENTATION IS ALREADY IN THIS REPO - COPY IT, DO NOT INVENT ONE.**
