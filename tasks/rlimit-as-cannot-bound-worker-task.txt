RLIMIT_AS bounds VIRTUAL ADDRESS SPACE, not resident memory. Each episode's Claude Code child is Node 22,
and V8 plus its thread pool RESERVE about 5.3 GiB and have peaked at 9.27 GiB, while actually using a
quarter of a gigabyte. A 3 GiB address-space cap on the worker is inherited by that child, so the child
cannot map what it needs and the episode dies. The resident figure the cap is meant to protect - 0.26 GiB -
is nowhere near it.

WHY THIS HITS PRODUCTION AND NOT JUST THE FALLBACK PATH: task 205 measured that on CT110, as user harness,
`systemd-run --scope` exits rc=1 with "Failed to start transient scope unit: Access denied" - a polkit
refusal - and PR #30's own fix makes ANY non-zero systemd-run exit choose the RLIMIT_AS retry. So on the
box that runs every harness episode, the fallback is not a fallback: it is the only path taken.

WHY THE PR'S TEST GAVE FALSE CONFIDENCE: its 7 passing tests ran under `ulimit -v 2500000` (2.4 GiB) and
passed because pytest is CPython, which reserves little address space. `claude --version` also starts fine
under 3G - verified. Neither exercises a real episode with MCP servers attached and stream-json output,
which is where the 5.3 GiB reservation appears. A test that cannot fail the way production fails is not
evidence.

    is the correct mechanism; make it WORK on CT110 rather than falling back. Options to evaluate and

    scopes; running the worker under the service's own delegated cgroup subtree (Delegate=yes in
    packaging/lh-harness.service, then write memory.max directly); or systemd-run --user with a user
    manager enabled for harness (loginctl enable-linger).
 2. IF an RLIMIT fallback is kept at all, it must not be RLIMIT_AS and must not be 3G. Use RLIMIT_DATA or
