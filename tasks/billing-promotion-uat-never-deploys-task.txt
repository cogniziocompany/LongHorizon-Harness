## THE MECHANISM - ESTABLISHED, DO NOT RE-DERIVE IT
`ci.yml` declares `on: push: branches: [main, develop, release]` and maps `release -> uat lane (CT100 :20253)`. So a push to `release` is SUPPOSED to deploy UAT.
The `release-ff` job in `promote-billing.yml` checks out with a bare `actions/checkout@v4` and runs `git push origin release`, so the push is authenticated with the **default `GITHUB_TOKEN`**. GitHub deliberately does not trigger workflows for pushes made with `GITHUB_TOKEN` - it is the documented guard against recursive workflow runs. The branch moves; nothing builds; UAT is never redeployed.
This is not a one-off. Every promotion through this workflow has had the same shape, which is why UAT has been sitting on a 2026-09-06 build.

## FIX - THERE IS ALREADY A WORKING REFERENCE IN THIS ESTATE; COPY IT
Do NOT invent a design. `cognizioware-powerplatform/.github/workflows/promote.yml` solves exactly this problem and is VERIFIED working: checked 2026-09-09, pp prod reports `version: sha-26d90ca` and the `main` branch is at `26d90caa` - they agree. That promotion does not move a branch and hope a push trigger fires; each stage **deploys directly** (checkout, then a rollout step with `GHCR_PULL_TOKEN`) and dispatches its QA gate with a dedicated `QA_GATE_DISPATCH_TOKEN` secret rather than the default token. Read it first and follow its shape.
