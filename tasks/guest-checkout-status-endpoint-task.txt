## WHY THIS EXISTS - AND WHY IT IS SMALL
Harness run `20260909T084904Z_caad6e1a` (task 53, powerplatform) stopped and asked rather than inventing a path:
the public Stripe return page must turn a Stripe `session_id` into `{paid, email}` for a **signed-out** buyer, and
there is no server-side way to do it. Verified independently in this repo, 2026-09-10:
`GuestSubscriptionController` is routed at `api/v1/guest` and exposes exactly three endpoints -
`POST checkout-session`, `GET customer-portal`, `GET subscription`. **None accepts a Stripe session id.**
**THE DATA ALREADY EXISTS - do not go to Stripe for it.** `GuestWebhookController` persists `CheckoutSessionId`
on the guest checkout-intent record and already looks rows up by exactly that field
(`FirstOrDefaultAsync(x => x.CheckoutSessionId == session.Id, ...)`). So this is a read over a row this service
already writes. **Read `GuestWebhookController` and `GuestSubscriptionController` before writing anything** and
follow their existing shape - DTOs, validation, logging, error envelope. Do not introduce a new pattern.

## WHAT TO BUILD
A single anonymous read endpoint on the EXISTING `api/v1/guest` controller - **do not create a new controller** -
that takes a Stripe checkout session id and returns whether it is paid, plus the payer email.
Return a shape that is honest about the three real states, and say in the report which you chose and why:
 **paid** | **not yet paid / still pending** (the webhook may not have landed) | **unknown session id**.
A pending webhook is NOT an error and must not read as one - it is the normal race immediately after redirect.

## SECURITY - THIS IS AN ANONYMOUS ENDPOINT AND THAT IS THE WHOLE RISK
It must be reachable without a login, which makes the session id the only thing standing between a stranger and
somebody else's email address. Treat that seriously and state your reasoning in the report:
 - Return the MINIMUM that the return page needs. Do not return subscription internals, customer ids, amounts,
   Stripe object dumps, or anything not required to render the page.
 - An unknown or malformed session id must return the SAME shape and timing as a known-but-unpaid one where you
   can - do not build an oracle that lets someone enumerate valid sessions by response differences.
 - Rate-limit or otherwise bound abuse if this repo already has a mechanism for it; if it does not, SAY SO and
   recommend rather than inventing one.
 - Never log the email at info level, and never log a full Stripe object.
If you conclude the email cannot be returned safely, say that plainly and return only the paid state - a smaller
honest endpoint is a better outcome than a leak.

requires no authentication; and no email appears in logs at info level.
