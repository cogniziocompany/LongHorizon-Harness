## ADDENDUM (Paxton, 2026-09-09) - VIEWING THE QUOTA PAGE, AND WHY THE OBVIOUS ANSWER IS BLOCKED

Paxton: *"Then create an iframe or something we can view it from ... then we can have chat.easy agent
exposed to their web pages and auth against them to manage and view."*

**MEASURED BEFORE YOU START - an iframe will NOT work. Do not spend rounds discovering this.**

    GET https://synthetic.new/quotas       -> HTTP 307,  x-frame-options: SAMEORIGIN
    GET https://synthetic.new/users/login  -> HTTP 200,  x-frame-options: SAMEORIGIN
    GET https://synthetic.new/             -> HTTP 307,  x-frame-options: SAMEORIGIN
    set-cookie: S=...; Domain=synthetic.new; Path=/; HttpOnly; SameSite

`x-frame-options: SAMEORIGIN` means **the browser refuses to render any synthetic.new page inside a
frame on ops.easybutt0n.ai.** There is no header we control that overrides it - it is the remote site's
choice. The session cookie is also `HttpOnly`, so page JavaScript cannot read or forward it.

So evaluate these, in this order, and implement the highest one that is acceptable:

**OPTION A - link-out (no credentials, always works).** A clearly-labelled link on admin-centres that
opens `https://synthetic.new/quotas` in a new tab, where Paxton's own browser session authenticates.
Zero secrets stored, zero moving parts. **Implement this unconditionally as the baseline**, because it
is strictly better than nothing and cannot break.

**OPTION B - server-side authenticated fetch, rendered as our own rows.** A small backend job logs in,
holds the session cookie server-side, fetches `/quotas`, parses the values, and renders them as native
rows next to the Ollama rows. This is the option that actually delivers thresholds and alerting.
**It requires storing Synthetic web-login credentials, which is a decision for Paxton, not for this
run.** Therefore:
  - **This task must NOT be given credentials and must not ask for them.** Build the mechanism so it
    reads from env NAMES that an operator populates later (e.g. a `SYNTHETIC_WEB_*` pair), document
    exactly which names, and leave them unset.
  - **Never write a credential into the repo, a doc, a KB article, a commit message, a PR body, a test
    fixture, or a memory file.** Env names only.
  - Deliver it switched OFF by default, so merging cannot start a login loop.
  - Say plainly in the PR body that Option B needs an operator step and Paxton's go before it does
    anything.

**OPTION C - browser agent (Paxton's "chat.easy agent" idea).** We already run Playwright containers on
CT202 (`cognizioware-mcp-tools-playwright-mcp`, `-playwright-qa1-mcp`, `-playwright-qa3-mcp`), so a
headless authenticated session is technically available without new infrastructure. **Do not build this
in this task.** Assess it only: state in the PR body what it would need (credential storage, session
lifetime, what happens on MFA, how a failed login is surfaced rather than silently retried) and whether
it is worth it once Option B exists. **Scope discipline matters more than coverage here** - this task
is already large, and an authenticated browser agent against a paid provider's account is its own piece
of work with its own security review.

**Applies to every option:** read-only. Do not click anything that purchases credits, modifies the
subscription, or triggers the monthly quota reset - **that reset is spent until ~2026-10-09.**

**Update to DONE MEANS:** in addition to the above, the admin-centres page must carry at minimum the
Option A link-out, and the PR body must state which of A/B/C were implemented and why, including the
`x-frame-options: SAMEORIGIN` finding so nobody re-proposes an iframe later.

**SECURITY - this is the part to get right, and it is not negotiable:**
 - `ops.easybutt0n.ai` is already behind `oauth2-proxy` on CT202. **Confirm that the new form is

 - **Secrets must NEVER be committed.** Not in the repo, not in a doc, not in a KB article, not in a

### PATH 2 - the agentic path: browser emulation

We already run Playwright on CT202: `cognizioware-mcp-tools-playwright-mcp`,
`-playwright-qa1-mcp`, `-playwright-qa3-mcp`. So the capability exists without new infrastructure.

 - Make an agent able to reach a session-authenticated provider page (Synthetic quotas, Ollama
   settings), read the usage values, and return them - **using a credential supplied at run time from
   the same store as Path 1, never one baked into code.**
 - **Handle failure honestly:** MFA, an expired session, a changed page layout, and a login that
   simply fails must each surface as a clear, distinguishable error. **A scraper that silently returns
   stale or zero values is worse than no scraper** - that is exactly the class of failure that let
   Synthetic's credit hit zero unnoticed.
 - **Rate-limit it.** Do not poll a provider's login page in a loop; a login storm looks like an attack
   on our own account. State the interval you chose and why.
 - Ship it **disabled by default**, requiring an explicit switch plus a credential to do anything.

### E2E FOR BOTH PATHS - required, and this is the part that makes it real

`e2e/suites/` is the home for these; follow the numbering and style of the existing suites.

 - **Path 1 e2e:** the form renders inside the authenticated route; a written value can be read back;
   the value is **masked in the DOM by default**; the reveal works; and - assert this explicitly - the
   secret **does not appear in page source, logs, or any committed artefact**. Use a dummy value.
 - **Path 2 e2e:** the browser-emulation route returns a usage value for a known fixture, **and** a
   failed/expired login produces a distinguishable error rather than a zero or a stale value.
   **Prove the failure case, not just the happy path.** A test that only asserts success would have
   passed all through the incident that prompted this task.
 - Both suites must pass with **no live provider calls and no real credentials** - stub the provider.
   The estate rule stands: no live calls to third parties from tests.

**Scope warning.** This task is now large: quota rows + thresholds + a credential form + an agentic
path + two e2e suites. **If it runs past its rounds, land Path 1 and its e2e first and say plainly
what is left** - Path 2 is the more valuable but also the more dangerous half, and a half-built

correct here; leaving something half-wired is not.
