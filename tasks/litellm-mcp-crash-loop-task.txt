WHY THIS MATTERS MORE THAN "IT SELF-HEALS" - this is the part I got wrong first
================================================================================

The restart is short and the container comes back, so this looked cosmetic. It is not. **The launcher
probes all three backends of a trio before every launch, and any probe landing in a restart window
fails at the transport layer**, not with a provider error:

    04:14  emit-probe [trio 4] manager/nemotron-3-super **HTTP Error 502: Bad Gateway**;
           executor/kimi-k3 **Remote end closed connection without response**;
           auditor/syn:large:vision **Remote end closed connection without response**
    04:14  HOLD - no trio had all three backends emit within budget

All three of those models answered **200 in about one second** twenty minutes later. So the sweep
was not seeing a sick provider - it was seeing our router bounce. **One restart = one failed sweep =
the whole queue (21 tasks) holds for a 15-minute cycle.** Seven restarts today.

It is also invisible: no operator surface shows a router RestartCount, so this has been happening
without anyone able to see it, and it gets misread as provider exhaustion every time.

================================================================================
WHAT TO DO
================================================================================

Two separate fixes; do BOTH, and do not conflate them.

1. **Contain the fault.** A single MCP server failing to list tools must not be able to terminate the
   proxy. Establish first WHERE the exception escapes - it is raised deliberately by
   `raise_classified_list_failure`, so something upstream is failing to catch it (a bare
   `asyncio.gather` without `return_exceptions=True` during startup/refresh is the likely shape).
   The `dataversedata` 403 is handled as a warning and survives, which proves the containment
   EXISTS on one path and is missing on another - find the difference between those two paths;
   that difference IS the bug.
   Prefer configuration over patching vendored library code. Check whether `mcp_servers` supports
   per-server disable/timeout, and whether the router can be told to treat list failures as
   non-fatal. **`mcp_servers` is one of the five DB-SHADOWED config sections - the DB row WINS over
   the YAML.** So a YAML-only edit may change nothing: use `POST /config/update`, then READ THE ROW
   BACK AND DIFF IT. Do not report success from a 200.

2. **Fix or remove the two broken servers.** `seq` and `dataversedata` are the trigger. Determine
   for each whether it should be reachable at all: if `dataverse-data-mcp:3120/mcp` returns 403 it
   is an auth/allow-list problem (this estate has had exactly that: a model 403'd for one key while
   answering for another); if `seq` is not meant to be registered on the prod router, unregister it.
   A server that cannot list tools is doing nothing useful either way.

Also add the one thing that would have made this visible: **surface the router's RestartCount on the
ops overview** so a bouncing router is legible. ops.easybutt0n.ai has SEVEN routes and the doctor
renders on **/overview** - EXTEND `infrastructure/docker/ops-control-center/doctor/ops_doctor.py`
and its `targets.json`. **Do NOT add a new view, a new route, or a /doctor route** - that is spec
drift and the estate rule forbids it.

THE MECHANISM OF THE LOOP - fix this, not the symptom:
  The container's command is `apt-get update && apt-get install -y libssl3 &&
  npm install -g @azure/mcp supergateway && npx supergateway --stdio 'azmcp server start'`.
  *** IT INSTALLS ITS OWN DEPENDENCIES FROM THE NETWORK ON EVERY SINGLE START. *** So each restart
  re-runs apt and npm, and a restart loop multiplies processes and page cache without bound. The fix
  is a BUILT IMAGE with azmcp and supergateway baked in, so a start is a start and not a build.
  Then find and fix whatever makes it exit in the first place.

*** A SECOND DEFECT THIS EXPOSED, AND IT IS THE MORE IMPORTANT ONE: ***
  Task 157 (PR #143) applied a mem_limit TO THE LITELLM CONTAINER ONLY. Capping one container and
  leaving its neighbours unlimited does not protect the host - IT SELECTS A VICTIM. The capped
  process is the one the kernel kills while the unlimited one does the hogging. That is exactly what
  happened: litellm (642 MiB, capped) died; azure-mcp-backend (15.7 GiB, uncapped) survived.
  THEREFORE: give EVERY container on CT202 a memory limit, sized from its measured steady state, and
  assert in a test that no container in the compose file lacks one. Coordinate with task 158
  (litellm router memleak) - do not re-cap litellm twice.
