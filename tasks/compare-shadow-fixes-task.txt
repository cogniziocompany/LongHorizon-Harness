DEFECT 1 (the big one) - judged on the shadow's LATEST decision, which is always post-launch.
  For entry 221 the shadow recorded `queue.shadow_launch` at 03:57:16Z (would_run_at), the PC
  launched run 20260923T035722Z_d1d74675 at 03:57:22Z, and every later shadow pass recorded
  `queue.shadow_skip` "workspace ... has active run 20260923T035722Z_d1d74675" - i.e. occupied by
  the PC's run OF THIS SAME ENTRY. The tool takes the latest record (a skip) and scores "missed".
  Same for 218 (shadow_launch 07:19:53Z, PC run 24b4a1ad at 07:19:54Z, then self-occupancy skips).
  FIX: compare the PC decision against the shadow's latest decision AT OR BEFORE the PC's launch
  time (within the cycle); and classify a skip whose occupying run_id equals the run the PC
  launched for this entry as `self-occupied` (neither agree nor missed), never as `missed`.
  Entry 217-clawdtalk shows the residual race: the PC launched before the shadow's first pass, so
  the shadow only ever saw self-occupancy. Classify that as `unobserved-race`, reported separately,
  and state how evidence item 3 should treat it.

DEFECT 2 - the documented --queue-names source does not survive.
  The shadow record carries queue_id and workspace but no entry name; without a map the tool keys
  shadow rows by workspace basename, so NOTHING joins (first run: agreement 0/139, every PC entry

  to build the map from runs_root/queue/q-*.json, but the PC launcher DELETEs each API entry at

  source is the PC log's own `shadow-filed <name>.json <queue_id>` lines. FIX: derive the map from
  the PC log by default; keep --queue-names as an override.

DEFECT 3 - the PC log carries HH:MM only; --pc-date must be exact for the FIRST line or every
  timestamp shifts (first run put 09-22 events on 09-30, +7 days, breaking the 900 s cycle window).
  FIX: either derive dates from an anchor the log itself carries (preferred: have launch_queue.py
  print a full ISO date line at startup and at each midnight roll - that is a PC-side change, state
