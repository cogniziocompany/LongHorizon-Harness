## CORRECTION 2026-09-09 12:40 PT - THE "7x" FIGURE IS WRONG. USE THIS INSTEAD.

Earlier in this file the local fallback is described as "about 7x less throughput". **That number is
misleading and must not be used to justify a routing decision.** Paxton challenged it and the
challenge was right.

How it was derived: local's best hour was 5,919,070 tokens; Synthetic was running ~44.7M tokens/hour;
44.7 / 5.9 = 7.6. That compares a PEAK to a RATE, across periods with different concurrency, and uses
TOKENS as a proxy for WORK.

The column that was not looked at, from LiteLLM_SpendLogs on CT202:

| hour (Z) | syn reqs | syn tokens/req | local reqs | local tokens/req |
|---|---|---|---|---|
| 11:00 | 273 | 47,554 | 1,170 | 1,102 |
| 12:00 | 326 | 52,039 | 3,606 | 1,162 |
| 13:00 | 257 | 38,725 | 3,600 | 1,565 |
| 14:00 | 0 | - | 3,531 | 1,676 |
| 17:00 | 263 | 37,072 | 3,704 | 1,070 |
| 18:00 | 777 | 49,945 | 5,179 | 255 |
| 19:00 | 692 | 60,932 | 2,372 | 873 |

**LOCAL MAKES MORE REQUESTS THAN SYNTHETIC** - 3,600/hr vs ~260/hr in several hours - but each local
request carries roughly **1,000 tokens against Synthetic's ~50,000**. That is a **~40x difference in
tokens PER REQUEST**, and it is what the "7x" was actually detecting.

**So the token ratio measures CONTEXT SIZE, not throughput and not productivity.** Synthetic's volume
is dominated by very large prompts being re-sent each round, consistent with 512k-context models.

### WHAT THIS CHANGES ABOUT THE TASK

**The cheapest lever may not be "move a role to local" at all.** If each Synthetic call carries ~50k
tokens, then **prompt/context size is the dominant cost driver**, and reducing what is re-sent each
round could save more credit than moving a whole role - without giving up model quality.

So add to Part 3, alongside per-role attribution:

 - **Measure tokens PER REQUEST per role**, not just totals. `LiteLLM_SpendLogs` has `prompt_tokens`
   and `completion_tokens` separately - **use the split**. If prompt_tokens dominate, the cost is
   context being re-sent, not work being done.
 - **Establish what is IN those ~50k-token prompts.** Whole-file dumps? Repeated workspace context
   every round? Accumulated conversation? Name it.
 - Then compare, with numbers, the three levers: (i) move a role to local, (ii) shrink the context
   sent per request, (iii) buy more capacity. **Do not assume (i) is cheapest** - that assumption is
   what this correction exists to kill.

**And do not repeat the original error:** never quote a tokens/hour ratio as a productivity or
throughput comparison without also reporting requests/hour and tokens-per-request. Token volume is not
work.

## MEASURED 2026-09-09 12:43 PT - PROMPT vs COMPLETION SPLIT, AND A TRAP IN IT

Ran the prompt/completion split this task asks for. Headline, 3-hour window, CT202:

| backend | reqs | prompt_tok | completion_tok | avg prompt/req | avg completion/req |
|---|---|---|---|---|---|
| SYNTHETIC | 1,812 | 95,485,888 | **3,828** | **52,696** | **2** |
| local | 12,466 | 7,529,207 | 160,240 | 604 | 13 |

**DO NOT read this as "100% of the cost is prompt tokens".** An average of **2 completion tokens per
request across 1,812 requests is not credible** - no useful model output is two tokens. That is
almost certainly **the streaming spend-logging bug from TASK 82**: the logger dies on streamed
responses (`cannot pickle '_thread.RLock'` inside `copy.deepcopy` in `spend_log_error_logger`), so
completion tokens go unrecorded while prompt tokens survive.

**Two conclusions, separated by confidence:**

1. **HIGH CONFIDENCE - Synthetic prompts are genuinely enormous: ~52,700 tokens per request**, against
   ~604 for local. That is ~87x more context per call, and it is the real cost driver to investigate.
2. **LOW CONFIDENCE / DO NOT USE - the prompt-vs-completion RATIO.** The completion side is
   under-recorded, so any "% prompt" figure is an artifact of the bug, not a property of the workload.

**THIS MAKES TASK 82 A DEPENDENCY, NOT A SIDE ISSUE.** The spend-logging bug is corrupting the exact
data needed to make this capacity decision. Until it is fixed:
 - `completion_tokens` cannot be trusted for streamed traffic,
 - and therefore neither can `total_tokens`, which means **every token figure in this task is a
   prompt-weighted FLOOR**, not a total.

**So the order matters: fix or characterise task 82's logging first, or state explicitly which of your
numbers survive it.** Do not build a routing recommendation on a column that is silently dropping data.

**What to do with the ~52,700-token prompts regardless:** that number does not depend on the broken
column, so it is actionable now. Find out what is IN them - re-sent workspace context each round?
whole-file dumps? accumulated conversation? - and whether the same work can be done with less context.
Halving the prompt halves the bill without changing a single routing decision.
