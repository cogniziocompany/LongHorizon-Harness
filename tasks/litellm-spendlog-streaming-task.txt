## THE FINDING - measured on the PROD router, 2026-09-09, over a 2-hour window

The router serves traffic correctly. It does NOT record all of it. Counts from the live container log:

    8422   HTTP 200 responses
       2   HTTP 500/502/503 responses          <- the request path is FINE
     533   "Spend tracking - update_database failed"
     533   "Error creating spendlogs object - maximum recursion depth exceeded"
     495   "TypeError: cannot pickle '_thread.RLock' object"

The traceback head names the operation:

    File ".../litellm/llms/openai/openai.py", line 1067, in async_streaming
    -> spend_log_error_logger.py:81 - Error creating spendlogs object
    -> File "/usr/lib/python3.13/copy.py", line 222, in _deepcopy_dict
    -> TypeError: cannot pickle '_thread.RLock' object

The spend logger deep-copies the request object to build a `LiteLLM_SpendLogs` row. On the STREAMING
path that object holds a live client handle containing an `RLock`, which `deepcopy` cannot pickle.
The response has already been served, so the user sees success and the cost row is lost.

**Why this matters beyond tidiness:** the harness routes nearly all executor traffic through the
streaming path. If streaming rows are the ones failing, `LiteLLM_SpendLogs` is missing most harness
usage, and every ranking, budget check or cost attribution built on that table is wrong in a way that
looks plausible. The overseer built a model-usage ranking on that table today and has withdrawn it.

Router image is digest-pinned: `ghcr.io/berriai/litellm@sha256:c8756e7b9a61...` (see the compose file
for the authoritative digest). Python 3.13 in-container.

*** WHAT IS ACTUALLY HAPPENING: THE `cannot pickle` ERRORS ARE **OUR OWN HOOK**, NOT LITELLM. ***
Same 6-hour window:

    "cannot pickle"                        1,772
    tracebacks at cache_namespacer.py      1,774      <- 1:1. They are the same event.

The failing line is **OUR** file, confirmed in the repo:
    infrastructure/docker/litellm/hooks/cache_namespacer.py:127   ->  `data = deepcopy(data)`
    (import at line 35: `from copy import deepcopy`)
The request dict carries `litellm_logging_obj`, which holds a `threading.RLock`. `deepcopy` cannot
pickle an RLock, so the hook throws every time. The live container file matches the repo file.

*** THE IMPACT IS RE-SCOPED, AND IT IS MORE SERIOUS THAN "MISSING COST ROWS". ***
The hook FAILS OPEN, so **no calls are lost and no spend rows are dropped by this**. But a request
whose hook threw is **never tenant-namespaced** - and the namespace is what prefixes the Redis cache
key (`caching.py _add_namespace_to_cache_key` reads `kwargs['cache']['namespace']`).
**So this is a CROSS-TENANT RESPONSE-CACHE ISOLATION GAP, not a cost-visibility bug.** That is a
security concern and it raises this task's priority above the framing it was filed under.

THE FIX IS HOOK-ONLY. **NO DIGEST CHANGE IS NEEDED FOR THIS.**
  * Replace `deepcopy(data)` with a shallow `data = dict(data)`, and copy only the cache sub-dict
    (`dict(...)` when it is a dict, else `{}`). **Nothing else in the function is mutated, so a
    shallow copy is correct** - do not reach for a deeper copy "to be safe"; that is what caused this.
  * Remove the now-unused `deepcopy` import and update the docstring.
  * **A test directory already exists**: `infrastructure/docker/litellm/hooks/tests/` (it holds
    `test_cache_namespacer.py` and `test_thinking_normalizer.py`). Add a case there whose `data`
    contains a real `threading.RLock()`. Assert: the namespace IS set, NO warning is logged, and the
    CALLER's dict and its original cache dict are UNCHANGED (the shallow copy must not leak mutations).
