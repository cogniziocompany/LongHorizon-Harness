ADDITIONAL INSTRUCTION FROM PAXTON (2026-09-08) - MSCE MUST COVER THE AGENT'S USE OF THE DEVICE FLEET. The architecture he confirmed, which corrects an earlier suggestion that one of the two fleet surfaces is redundant (neither is; they are different planes):
 - The FLEET VIEW (fleet.easybutt0n.ai) shows ALL lh-harness runs - it is the wallboard for everything running anywhere.
 - HYDRA is the DEVICE fleet and the control plane: real-time execution surfaces - terminals, shells, heads on machines.
 - Each lh-harness run is an AGENT that may reach into Hydra's device fleet to actually execute (bash, a terminal head, a device). So a run is not only a row in a list; it is a consumer of devices, and the pairing between the two is the thing a person needs to see.
WHAT THIS MEANS FOR THE MSCE LAYERS you are building - carry the device dimension through all three levels, using the same identifiers everywhere so a trace can be joined to a fleet row and to a terminal:
 - L1 (trace): every TraceUnit that involved a remote execution must record which device/head/terminal it used and on which Hydra host, alongside the tool_names it already carries - at minimum a device id, a session/terminal id if one exists, and the Hydra node the exec went through. If the round did no remote exec, the fields are absent, not empty strings. These ids must be the identical strings Hydra and the fleet surfaces use; never re-key or truncate them.
 - L2 (policy): when the same device-shaped action recurs across separate tasks, the generalized routine must keep the device REQUIREMENT (what kind of head, what shell, what constraints) while dropping the specific instance - a policy is "needs a linux shell head on a fleet device with docker", not "used head 7 on desk03".
 - L3 (environmental cognition): the stable knowledge about the device fleet itself belongs here - which hosts exist, what each can run, the constraints the overseer already knows (for example: no host-level changes without an explicit go; a runner restart is issued from OUTSIDE the runner; some hosts have no IPv6 egress), and the tool inventory a head exposes. This is exactly the "file structures, rules and tool constraints" the framework describes, applied to the fleet.
 - REDACTION still applies to every one of those fields; device ids and host names are fine, tokens and keys are not.
WHY (the use case, in Paxton's words): "I user access hydra, can see all the harness in the right side panel, then if any are using the hydra tools, I should see it in the terminal and the heads on the left hand side of the screen." The experience layer is what makes that correlation durable after the fact - so that a run's history explains which devices it drove and a policy learned from it can say what kind of device it will need next time.
SCOPE GUARD: this instruction adds FIELDS and their capture, not a new subsystem. Do not add a Hydra client, do not call Hydra, and do not make the harness depend on the device fleet being present - the fields come from what the run already knows about its own tool calls.
