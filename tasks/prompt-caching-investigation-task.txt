## WHAT IS ENABLED - read from the DEPLOYED config on CT202, not from the repo

    litellm_settings:
      cache: true
      cache_params:
        type: redis
        host: os.environ/REDIS_HOST
        port: os.environ/REDIS_PORT
        password: os.environ/REDIS_PASSWORD
        ttl: 300

The config's own comment says: *"Backing store: in-stack `redis` service (docker-compose.yml). Purpose
is cost caching - hence the deliberately short 300s TTL."* The `cognizioware-mcp-tools-redis`
container is **Up 21 hours (healthy)**, so the backend is fine.

## AND IT IS ACHIEVING NOTHING WHERE IT MATTERS - measured, 6-hour window

From `LiteLLM_SpendLogs.cache_hit` on CT202:

| backend | cache_hit | requests | prompt tokens |
|---|---|---|---|
| **SYNTHETIC** | **False** | **2,107** | **111,654,216** |
| local | False | 20,662 | 18,166,274 |
| local | None | 2,404 | 8,248 |
| local | **True** | **71** | 43,979 |

**Synthetic: 2,107 requests, ZERO cache hits.** Local: 71 hits out of ~23,000 (0.3%).

**The hypothesis to test (do not assume it - prove or refute it):** LiteLLM's `cache: true` is
**exact-match RESPONSE caching** - identical request in, stored response out. Harness agent rounds are
never byte-identical, because the conversation grows every turn, so a 300s exact-match cache can
essentially never hit on this traffic. If that is right, **the cache that is enabled is the wrong KIND
of cache for our problem**, and the 300s TTL is irrelevant either way.

## WHY THIS MATTERS - the number it would attack

Synthetic averages **~52,700-55,000 PROMPT tokens per request** (two independent windows agree),
against ~604 for local models - roughly **87x more context per call**. Prompt volume is the dominant
cost driver, and the weekly credit ran out on 2026-09-09 with **no manual reset available until
~2026-10-09**.

**So: if a large, stable prefix is being re-sent every round, prefix/prompt caching is the lever that
costs nothing in model quality and requires no routing change.** That is a far better first move than
moving roles onto local hardware.
