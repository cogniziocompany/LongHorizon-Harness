ITEM C - the Environments "Refresh" button is permanently wedged
--------------------------------------------------------------------------------

Rows say "Never refreshed - refresh before starting a session", and Refresh returns:
"A refresh is already running for this environment. Please contact Cognizioware support..."

TWO INDEPENDENT DEFECTS COMPOUND. A durable DB lock nothing can release, plus a frontend that never
refetches while it is held - so the row keeps saying "Never refreshed" with the button ENABLED,
guaranteeing the user re-clicks into the same 500 forever.

C1 - BACKEND, a permanent lock (environment-refresh.service.ts):
  - :244-246 guard throws when refresh_state === 'running'.
  - **NO `finally`** - the lock is released only on the happy path (:252-271). The catch itself does
    two DB writes; if either throws, the rejection is unhandled inside a bare setImmediate and the row
    stays 'running' FOREVER.
  - **The executor is in-process `setImmediate`** (:203-211, :253). The LOCK is durable (DB) but the
    EXECUTOR is only in RAM. Any restart, deploy, OOM-kill or crash between setRefreshToken (:109-125,
    called :250) and the terminal updateRefreshState wedges the environment permanently. Nothing binds
    the lock to the owning instance. **This is the likely production trigger.**
  - **No TTL, no reaper.** refresh_started_at is written (:120) and read (:84) but never compared
    against NOW() anywhere in the tree.
  - **No fetch timeouts.** fetchJson (:127-140) makes 4+ unbounded fetches to Dataverse (:155-158,
    :188) with no AbortSignal - a hung Dataverse call holds the lock indefinitely.
  - The check-then-set is **NOT ATOMIC**: SELECT :226-231, if :244, separate UPDATE :250, no
    transaction, no FOR UPDATE. Two concurrent clicks can both pass.

  FIX - one statement gets atomicity AND stale-lock expiry, with no separate reaper:
      UPDATE ... SET refresh_state='running' ...
       WHERE id=$1 AND user_email=$2
         AND (refresh_state <> 'running' OR refresh_started_at < NOW() - INTERVAL '<ttl>')
      -- treat "0 rows updated" as the conflict
  Plus: wrap the scheduled work in try/catch/finally so the terminal state write happens on EVERY
  path, and make the catch itself failure-tolerant (a throw in logRefreshIncident must not skip the
  state write). Add AbortSignal.timeout(...) to fetchJson, sized UNDER the lock TTL.

  **TTL is a judgement call - it must exceed the slowest legitimate refresh.** 15 minutes is the value
  in the unblock SQL. Validate against real refresh durations before hardcoding; state what you chose
  and why.

C2 - BACKEND, the conflict is misclassified as a 500:
  AppError('E901') is the INTERNAL error code - cgz-codes.ts E901 block ~:127 is httpStatus 500,
  machineName 'internal_error', fixText "Please contact Cognizioware support and include the incident
  number." That fixText is verbatim the banner's second line. **A routine concurrency conflict is
  reported as a 500 with a logged incident, and the user is told to contact support for something that
  should self-resolve.**
  FIX: add a dedicated 409 conflict code (e.g. refresh_in_progress) with actionable fixText. No such
  code exists today. Reserve E901 for genuine internal errors.

C3 - FRONTEND, never refetches while the lock is held (EnvironmentList.tsx):
  - button disabled={isRunning || isInactive || env.is_production}, isRunning from
    env.refresh_state==='running' (:389, button :452-467)
  - refreshEnvironment (:261-274) POSTs then only setPollingEnvId - it NEVER optimistically sets local
    refresh_state='running'
  - the 2s poll (:195-217) calls loadData() ONLY once status.refreshState !== 'running'
  FIX: set refresh_state='running' locally on a successful POST (disables the button immediately), and
  have the poll update the row's displayed state on EVERY tick, not only on completion.
