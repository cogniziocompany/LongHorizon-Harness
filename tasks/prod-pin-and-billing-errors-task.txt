## DEFECT 1 - THE PROMOTION LEAVES PROD ONE `compose up` AWAY FROM REVERTING
The prod lane box carries `/opt/cognizioware-powerplatform/.env` with `APP_IMAGE_TAG=<sha>`, and `docker-compose.yml` resolves `image: ...app:${APP_IMAGE_TAG:-latest}`. The promotion deploys a new sha to prod but DOES NOT update that pin. On 2026-09-08 the pin still read `sha-998b2e0` (an August build) while prod was serving the promoted `sha-e5c903b`. An operator ran `docker compose up -d --no-deps app` for an unrelated reason and compose silently rolled production back to the August image; it served the wrong build for about twenty minutes and reported version `1.0.0-local`. Nothing failed loudly - the container came up healthy on the wrong code.
FIX: the promotion's prod deploy step must WRITE the deployed sha into that box's `.env` as part of deploying, so the file and the running container always agree. Then add a post-deploy assertion that reads the pin back and fails the deploy if it does not match what was just deployed - a write you do not verify is the same class of bug as the one you are fixing. Do the same for the uat and dev stages if they share the pattern; say which stages you changed. Consider whether the deploy script should also refuse to start when `APP_IMAGE_TAG` is unset rather than falling back to `:latest`, and say what you decided and why - `:latest` on a prod box is its own quiet hazard.
Read `scripts/deploy/rollout.sh` and `.github/workflows/promote.yml` first; the fix belongs wherever the deploy already writes to the box, not in a new script.

## DEFECT 2 - EVERY BILLING VERIFICATION FAILURE SAYS THE SAME WRONG THING
`packages/backend/src/services/auth.service.ts`, `fetchBilling()`: any non-OK response from `GET {BILLING_API_URL}/api/user-org?email=...` produces `"Email not found in billing system. Sign up for a free trial."` and a redirect to `/signup?mode=guest`. So a 401, a 500, a timeout and a genuine 404 are indistinguishable to both the user and the operator.
On 2026-09-08 powerplatform prod was sending a 24-character billing key while the billing service ran a 48-character one. EVERY lookup 401'd, and every user saw "Email not found in billing system" - including accounts that were present in billing all along. An hour went into looking for missing customer records that were never missing.
FIX: distinguish the cases and say something true for each.
 - 404 -> genuinely not a customer. Keep the current message and the signup redirect.
 - 401/403 -> we cannot authenticate to billing. This is OUR misconfiguration, not the user's problem. Say so plainly, do NOT offer a free-trial signup, and log loudly enough that an operator notices - this condition affects every user at once.
 - 5xx / network / timeout -> billing is unreachable. Say it is temporary and that retrying may help.
Return a machine-readable reason alongside the human message so the frontend can act on it, and NEVER let an infrastructure fault present as a customer-status fact.
FRONTEND: the Retry button on the session-setup verification banner currently re-runs the same call and shows nothing new; under a 401 it can never succeed, so it reads as a dead control. Make it surface the distinguished reason, and where retry cannot help (401/403), say that instead of inviting a retry that will fail identically. Find it in the frontend package rather than assuming the file; keep the change small.

Billing is a COMMERCIAL signal, and a commercial signal must never be the thing that stops a tenant-authenticated user working.

THIS IS ABOUT **OUR APP'S OWN DEPLOYMENT ENVIRONMENT**, NOT A DATAVERSE ENVIRONMENT. Read that twice - they are unrelated and easy to confuse. Keep it CHEAP AND QUICK - a client-side guard on the controls, in the style the app already uses. This is deliberately not a permissions system: the server still decides everything that matters, and a user who defeats the client-side guard hits the same server behaviour they would have anyway.
The billing status the UI keys off must come from the EXISTING billing signal the app already has - do NOT add a second source of truth for whether someone has paid.
