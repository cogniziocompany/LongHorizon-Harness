## THE PRINCIPLE
`withInfraRetry` classifies by ERROR SHAPE, and a timeout has no shape. A request that never returns is at least
as strong evidence of an infrastructure problem as one that returns 429 - a healthy backend answers, and an
assertion cannot fail if it never ran. Today the gate's own retry loop guarantees the wrong verdict on the
harder case: the more thoroughly a provider is broken, the more likely it stalls rather than replies.

## WHAT TO CHANGE
Treat a client-side timeout or aborted request against a model endpoint as an INFRA result, not a test failure -
the same disposition a 429 already gets. Read `packages/runner/src/infra-retry.mjs` first and follow its existing
classification structure rather than adding a parallel path. Points of judgement, decide them and SAY WHY:
 - Distinguish a timeout on the REQUEST from a timeout in the harness itself. Only the former is infra.
 - The retry budget matters: `kimi-k3:cloud` consumed 90s once, while `glm-5.3-flash:cloud` consumed 183s over
   three attempts. A stalling provider must not be retried until the job's own limit - cap total time spent on a
   single model and record what it cost.
 - **Do not make the gate unable to fail.** The whole point of the score is that a genuine regression still turns
   it red. If EVERY suite result is infra, the gate must report blocked-by-infrastructure - the machinery for
   that already exists (`description="blocked by infrastructure: ${infra_reason:-rate-limit/router outage}"`) -
   NOT report success. Reclassifying must move a result from `failed` to `infra`, never from `failed` to `passed`.
 - Say plainly in the report which models were skipped and why, so an operator reading a green-ish gate can see
   that coverage was reduced.

## ADDED 2026-09-09 23:25 - THE MECHANISM IS VERIFIED, AND SO IS THE RISK. READ BOTH.
**Why this fix genuinely unblocks deploys rather than just relabelling a failure.** Traced through
`.github/workflows/qa-gate.yml`: the suite step runs `npm test` with `continue-on-error: true`, and the job's
verdict comes from a single later step - `Fail the job if the suite failed`, `if: steps.suite.outcome != 'success'`
-> `exit 1`. It keys on the **exit code of `npm test`**, not on the gate report's score. Node's test runner counts a
SKIPped test as passing, which is exactly why the `glm-5.3-flash:cloud` infra-skip did NOT fail the job on its own
while the `kimi-k3:cloud` timeout did. So reclassifying a timeout as infra turns it into a SKIP, `npm test` exits 0,
the job passes and the deploy proceeds. That is the whole causal chain; you do not need to rediscover it.

**And that is precisely why the guardrail in this brief is not optional.** The same mechanism means a TOTAL provider
outage would skip every model, exit 0, and wave every deploy through with the router suite having proven nothing.
An all-infra run MUST report blocked-by-infrastructure and must not exit 0. Treat that as the acceptance criterion
of this task, not a nicety - without it this change converts a noisy gate into a silent one, which is worse than
what it replaces.
