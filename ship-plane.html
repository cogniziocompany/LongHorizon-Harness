The 5-minute audit loop

A scheduled sweep runs every 5 minutes as part of the standing goal and updates this page when something changes. It goes to full depth on every tick while a run is on the local model or fewer than two provider keys are healthy, and drops to a quick pass otherwise. Six steps, in order:

  1. Harness fleet plane Keep the Hydra orchestrator on corsairai300 and the fleet window running, and confirm the harness node is still registered as an online external node holding its token. Three known traps are checked every time: a deploy can wipe the node variables from the live environment file, recreating the orchestrator orphans the tunnel that shares its network namespace, and a slim image can fail a health probe that shells out to a binary it does not ship.
  2. Harness runs Resolve every run waiting at a gate, revive or requeue the failed ones, and never leave two runs on one working tree.
  3. Deploy lanes Check the newest run on each repo's default branch, diagnose and re-run anything red, against a checklist of the traps that have bitten before.
  4. Open pull requests Merge what is green so its own pipeline deploys it, queue an integration task for anything conflicting, close what is superseded.
  5. Production health A cheap probe of each public surface, never the bare gateway health route, which bills a completion against every model.
  6. Capacity Keep the launcher and the quota watcher alive, keep the queue draining, and route a blocked priority task to a parallel working tree.

The path of one change

  1. Task text The overseer, or the chat agent at chat.easybutt0n.ai, writes a scoped task (repo, branch, deliverables, hard rules) and enqueues it. Today that is a JSON entry in the queue folder on this PC; after the CT110 release it is the harness queue (POST /api/queue, the chat's lhharness tool, or the Hydra panel), and the queue chooses a model per role from what is actually available and records why (task 49).
  2. Harness run on CT110 The launcher starts an lh-harness run: manager plans, executor builds in the repo workspace, auditor checks each round. Gates pause for decisions.
  3. Review + PR The overseer reviews the branch (diff, tests, secret scan), pushes it and opens the pull request. Nothing merges without this step.
  4. Lane Merging triggers the repo's deploy lane on the CT210 runners: E2E gate, UAT apply, UAT QA gate, prod deploy, smoke, prod QA verify. Gates decide, not people.
  5. Verify + record The overseer verifies the live result, writes the outcome into tasks/*.md, and queues any follow-up as a new task.
